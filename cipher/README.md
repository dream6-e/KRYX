# KX1 — Luau 专属流密码

自研算法，**刻意依赖 Luau 运行时语义**，使静态照抄到其他语言时必然偏离。
不追求密码学强度（远低于 ChaCha8），追求「看懂了也难复现」。

| 文件 | 说明 |
|---|---|
| `kx1.lua` | 算法实现（8.9 KB） |
| `test_kx1.lua` | 自测 27 项，全通过 |

```bash

  echo 'end)()'; cat cipher/test_kx1.lua; } > /tmp/run.lua
./toolchains/bin/luau /tmp/run.lua
```

## 结构

```
key (任意长度)
  └─→ keywords()  16 个 32 位字，用 KX1 自身扩散 3 轮
        └─→ stream()  64 位计数器，每块 +1
              └─→ block_enc()  8 轮，两组 4 字 ARX + 交叉
```

- **块大小**：8 字节（8 个 32 位字）
- **输出模式**：计数器流（CTR），加密 = 明文 XOR 密钥流
- **nonce**：32 位，展开成 64 位计数器初值
- **性能**：约 2.7 MB/s（纯 Lua，未优化）
- **密钥调度**：约 0.07 ms / 次

## 核心：6 条 Luau 语义锁

算法把这些点埋进轮函数，任何「正常写法」的移植都会在这里偏掉。

### 1. `bit32.lshift(x, n)` 对 n ≥ 32 返回 0（不掩码）

```lua
bit32.lshift(0x12345678, 32)  -->  0        -- Luau
x << (32 & 31)                -->  x        -- C/C++（实际多为 UB）
x << (32 & 31)                -->  x        -- JS
```

`quarter()` 里有：

```lua
s[c] = BXOR(s[c], LSH(r1 + r2, round * 8 + r1))
```

第 5 轮时 `round*8 = 40 > 32`，整项塌成 **0**，当轮失去一半混合。
移植版会得到非零值 —— 字节流从此分岔。

### 2. `bit32.rrotate(x, n)` 掩码；`lshift`/`rshift` 不掩码

同一份代码里两种越界语义并存：

```lua
bit32.rrotate(0x12345678, 33) == bit32.rrotate(0x12345678, 1)   -- 掩码
bit32.lshift(0x12345678, 33)  == 0                              -- 塌成 0
```

### 3. `bit32.*` 对非整数**向零截断**，负数按 mod 2³²

```lua
bit32.bxor(-1.5, 0)  -->  4294967295     -- -1.5 → -1 → 0xFFFFFFFF
bit32.bxor(2.7, 0)   -->  2
```

Python 的 `~`、C 的负右移、JS 的 `|0` 在这里给出不同结果。

### 4. `%` 是 floor 语义，`math.fmod` 是 trunc 语义

```lua
(-7) % 3        -->  2
math.fmod(-7,3) --> -1
```

C 的 `%` 与 Python 的 `%` 对负数给**相反**符号。

### 5. 数字是 IEEE double，32 位数相乘丢低位

这一条最刁钻。Luau 里：

```lua
0xFFFFFFF * 0xFFFFFFF          = 72057593501057024     -- 丢精度
精确值                          = 72057594021150721
取低 32 位：Luau = 3758096384，精确 = 3758096385      -- 差 1
```

所以算法**必须**用 `mul32()`（16 位分肢）才可逆：

```lua
local a0 = a % 65536
local a1 = (a - a0) / 65536
return (a0*b0 + ((a0*b1 + a1*b0) % 65536) * 65536) % U32
```

反过来 —— **照抄的 Python / C 实现因为整数精确，反而不等于 Luau 的结果**。
这条把「移植」这个方向直接堵死了。

### 6. `buffer.writeu8` 越界值 mod 256，不报错

```lua
buffer.writeu8(b, 0, 300)   -->  buffer.readu8(b,0) == 44
buffer.writeu8(b, 0, -1)    -->  255
buffer.writeu8(b, 0, 1.9)   -->  1
```

严格检查的语言会直接抛异常。

## 自测覆盖（27 项）

| 组 | 内容 |
|---|---|
| 1 | `mul32` 与精确值一致（6 组，含 4 组朴素实现会差 1 的） |
| 2 | 确定性 |
| 3 | 雪崩：key / nonce 改 1 bit → 比特差落在 35%~65% |

## 强度说明（如实）

**不强。** 对比：

| | KX1 | ChaCha8 |
|---|---|---|
| 轮数 | 8 | 4 双轮 (= 8 轮) |
| 字宽 | 32 | 32 |
| 每轮操作 | ARX + 乘法 + 位计数 + 字节交换 | 纯 ARX |
| 密钥 | 16 字 | 8 字 |
| 已知分析 | 无 | 广泛 |
| 抗差分/线性 | **未评估** | 有界 |

**明确不保证**：抗差分密码分析、抗线性密码分析、抗相关密钥攻击。
`BYSWAP`、`CNTLZ`/`CNTRZ`、非双射的四则混合都可能引入可利用的结构。

它的定位是**混淆层**，不是安全边界。真正的安全来自不让人知道算法 ——
这一点和项目里其他层（数字进制转换、转义编码）是同一档，只是这件做得更细。

## 为什么这样设计能达成「静态难复现」

破解放手通常的做法是：把 Lua 算法逐行译成 Python，跑一遍对比输出。

本算法对这条路设了 3 道坎：

1. **语义坎** —— 6 条锁里有 4 条（1/3/4/6）在常见语言里行为不同，
   译过去不会报错，只会**静默产出不同字节**
2. **精度坎** —— 第 5 条让「精确计算」反而错，而这正是 Python/C 的默认行为
3. **验证坎** —— 没有输出向量对照，作者自己也不知道译错了

第 3 道坎本来最弱（附录输出向量就能破），但混淆产物里不该带向量。
生产环境中 `M.E` / `M.R` / `M.mul32` 这些导出应当移除。

## 接入混淆器时要做的事（本次未做）

1. 删掉 `M.mul32` / `M.E` / `M.R` 导出
2. 常量 `E` / `R` / `MA` / `MB` 改由生成器随机产生并内联（现在写死在源码里，
   `grep 0x6B72797A` 就能定位）
3. 函数名经 `Names::shrink` 处理
4. 轮数 8 可在 6~10 之间随机
5. 与现有 `chacha8_xor` 二选一或串联 —— **不建议串联**，
   两层纯 Lua 流加密在 100 KB 载荷上会让启动慢到不可接受
